# ADR-004 — เก็บ bitmap สองความละเอียด: display สำหรับจอ, blob ต้นฉบับสำหรับ export

- สถานะ: **ตัดสินใจแล้ว** (Phase 0)

## การวัดจริง (spike S2)

**20 รูป ขนาด 3840×2160 (สกรีนช็อต 4K):**

| | chromium | firefox | webkit |
|---|---|---|---|
| เวลา decode รวม | 457 ms | 578 ms | **1767 ms** |
| ต่อรูป | 22.9 ms | 28.9 ms | **88.3 ms** |
| ย่อลง 2048px | 237 ms | 517 ms | 303 ms |
| **หน่วยความจำถ้าเก็บความละเอียดเต็ม** | **664 MB** | 664 MB | 664 MB |
| **หน่วยความจำถ้าเก็บ display 2048px** | **189 MB** | 189 MB | 189 MB |

**5 รูป ขนาด 1440×12000 (สกรีนช็อตเต็มหน้า):** decode 156 / 244 / 1407 ms

## ข้อค้นพบ
1. การเก็บ bitmap ความละเอียดเต็มไว้บนจอ กิน **664 MB สำหรับแค่ 20 รูป** — ยอมรับไม่ได้
2. การย่อเหลือ 2048px ลดเหลือ **189 MB (−72%)** โดยไม่กระทบคุณภาพที่มองเห็น เพราะไม่มีใครดู 4K เต็มบน board กว้าง 1200px
3. **WebKit decode ช้ากว่า Chromium ~4 เท่า** — งบ "20 รูป < 2 วินาที" บน Safari เหลือที่หายใจน้อยมาก

## การตัดสินใจ
- เก็บ `Blob` ต้นฉบับไว้เสมอ → ใช้ตอน export เท่านั้น (decode ใหม่ที่ความละเอียดที่ต้องการ ไม่เสียคุณภาพ)
- สร้าง **display bitmap** ย่อให้ด้านยาวสุด ≤ 2048px → ใช้วาดบนจอ
- decode ใน Web Worker และประมวลผลทีละ 4 ไฟล์ พร้อมแสดงความคืบหน้า
- ปล่อยทรัพยากรทันทีเมื่อลบ node: `bitmap.close()` + revoke object URL + ลดตัวนับ reference
- นับ reference ด้วย content hash เพื่อไม่ให้รูปเดียวกันที่ duplicate กินหน่วยความจำซ้ำ

## ผลที่ตามมา
- ⚠️ ต้องตั้งงบประสิทธิภาพของ Safari แยกจาก Chromium — Safari คือ worst case เสมอ
- ⚠️ ต้องมี placeholder ระหว่าง decode เพราะบน Safari ผู้ใช้จะรอเห็นได้ชัด
