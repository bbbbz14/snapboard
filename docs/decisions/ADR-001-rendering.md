# ADR-001 — ใช้ Canvas 2D renderer ที่เขียนเอง ตัวเดียวสำหรับทั้ง preview และ export

- สถานะ: **ตัดสินใจแล้ว** (Phase 0, 2026-09-10)
- ทางเลือกที่พิจารณา: DOM+CSS แล้ว export ด้วย html2canvas · Konva/Fabric · Canvas 2D เขียนเอง

## บริบท
ความเสี่ยง R1 ("export ออกมาไม่เหมือนที่เห็นบนจอ") เป็นความเสี่ยงที่ร้ายแรงที่สุดของผลิตภัณฑ์นี้
เพราะทางออกของผู้ใช้คือไฟล์ภาพ ถ้าไฟล์ไม่ตรงกับสิ่งที่เห็น ผลิตภัณฑ์ก็ไร้ค่าทันที

## การวัดจริง (spike S4, 3 เบราว์เซอร์)
สร้าง scene 9 รูป + ข้อความ + ลูกศร + กล่อง + พื้นที่เซ็นเซอร์ แล้ววัด:

| ตัวชี้วัด | chromium | firefox | webkit |
|---|---|---|---|
| Parity A — export ผ่าน OffscreenCanvas→PNG→decode เทียบกับ preview (ค่าผิดพลาดสูงสุดต่อ channel) | **0** | **0** | **0** |
| Parity A — ค่าผิดพลาดเฉลี่ย | **0** | **0** | **0** |
| Parity B — landmark ที่ scale 2 อยู่ที่พิกัด ×2 พอดี | ✅ | ✅ | ✅ |
| hit-test ที่เขียนเอง (100 node) | 1.2 µs | 0.8 µs | 0.9 µs |

## การตัดสินใจ
ใช้ `renderScene(ctx, scene, { scale })` **ฟังก์ชันเดียว** ขับทั้งการแสดงผลบนจอและการ export
DOM ใช้เฉพาะ overlay บาง ๆ (handle ปรับขนาด, textarea ตอนพิมพ์, toolbar ลอย)

**ไม่ใช้ Konva/Fabric** เพราะ:
- scene ของเราไม่มีการหมุน → hit-test เป็น AABB ล้วน วัดได้ ~1 µs และเขียนจริงแล้วใน spike ใช้โค้ด ~60 บรรทัด
- prototype renderer ที่ครอบคลุม image+เงา+ขอบมน / text พร้อมตัดบรรทัด / ลูกศร / กล่อง / pixelate ใช้ **~300 บรรทัด** — ต้นทุนต่ำกว่าการเรียนรู้และสู้กับ API ของ library
- ควบคุม pipeline การ export และ DPI ได้เต็มที่

**ไม่ใช้ html2canvas** เพราะเป็นการสร้างความเสี่ยง R1 ขึ้นมาเองโดยไม่จำเป็น

## ผลที่ตามมา
- ✅ ความเสี่ยง R1 ถูกกำจัด **โดยโครงสร้าง** ไม่ใช่ด้วยการทดสอบ — วัดได้ค่าผิดพลาด 0 ทั้ง 3 เบราว์เซอร์
- ✅ export ที่ 2x/3x = เรียกฟังก์ชันเดิมด้วย scale ต่างกัน
- ⚠️ ต้องเขียน hit-test / handle / marquee เอง (ประเมินไว้ ~1 วัน)
- ⚠️ a11y ต้องออกแบบเพิ่ม เพราะ canvas ไม่มี semantics — ชดเชยด้วยการทำให้ทุกคำสั่งมีคีย์ลัดและมี ARIA live region
- 🔁 ทางถอย: ถ้า Phase 1–2 ช้ากว่าแผนมาก ย้ายไป Konva ได้โดยไม่แตะ scene model เพราะ renderer ถูกแยกออกจาก state แล้ว
