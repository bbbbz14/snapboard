# Phase 1 — Core loop: วาง → จัดวางอัตโนมัติ → คัดลอก · เสร็จสิ้น

วันที่: 2026-09-10 · ผลรวม: **ทดสอบผ่าน 148/148** (72 unit + 27 renderer parity + 49 e2e) บน Chromium, Firefox, WebKit

## วัตถุประสงค์
ทำวงจรคุณค่าหลักให้ครบตั้งแต่ต้นจนจบ — วางรูปแล้วได้ภาพที่ส่งได้ โดยไม่ต้องแก้อะไรเลย

## ข้อค้นพบระหว่างทำ Phase 1

### 1. 🐛 บั๊กจริงที่การทดสอบ parity จับได้ — export ไม่เหมือนที่เห็น
`exportBoard` สร้าง canvas context ด้วย `{ alpha: false }` เมื่อพื้นหลังทึบ
Chromium จึงสลับไปใช้ **subpixel antialiasing** กับตัวอักษร ทำให้ตัวเลขใน badge
ที่ export **ต่างจากที่เห็นบนจอสูงสุด 100 ระดับต่อ channel**

นี่คือความเสี่ยง R1 ตัวเป็น ๆ ที่ Phase 0 บอกว่าต้องกลัว และมันหลุดเข้ามาจริง
แก้แล้วโดยให้ทั้งสองเส้นทางใช้ค่า alpha เดียวกัน · จะสำคัญมากขึ้นอีกใน Phase 4 ที่มีเครื่องมือข้อความ
→ [ADR-007](../decisions/ADR-007-tile-parity-tolerance.md)

### 2. 🐛 บั๊กที่ unit test จับได้ — gutter ของเลขขั้นตอนถูกลบทิ้ง
`finalize()` เลื่อนเนื้อหาให้ชิด padding โดยคำนวณจาก bounding box ของรูปเท่านั้น
ทำให้ช่องว่างซ้ายที่กันไว้ให้เลขขั้นตอน **หายไปทุกครั้ง**
แก้โดยให้พื้นที่ที่กันไว้เข้าร่วมการคำนวณ bounds

### 3. 🎨 ปัญหา UX ที่เห็นได้จากสกรีนช็อตเท่านั้น
โหมด Steps เดิมจัดรูปกึ่งกลาง ทำให้ภาพขนาดต่างกันเรียงเป็นซิกแซก อ่านลำดับไม่ได้
เปลี่ยนเป็น **ชิดซ้าย** เพื่อให้สายตาไล่ลงมาตามขอบเดียว
และพบว่า gutter ที่กันไว้ **ว่างเปล่า** เพราะเลขลำดับถูกวางแผนไว้ที่ Phase 4
→ ตัดสินใจ **เลื่อน badge เลขขั้นตอนขึ้นมาทำใน Phase 1** เพราะโหมดที่กันที่ว่างไว้แล้วไม่วาดอะไร แย่กว่าไม่มีโหมดนั้นเลย

### 4. ✅ คำสัญญา privacy กลายเป็นการทดสอบแล้ว
`tests/e2e/privacy.spec.ts` ยืนยันว่าหลังโหลดหน้าเว็บ ทำงานครบวงจร (วางรูป → เปลี่ยนโหมด → export)
แล้ว **ไม่มีคำขอเครือข่ายใดที่มี body, ไม่มี method ที่ไม่ใช่ GET, ไม่มี origin อื่น**
สิ่งเดียวที่โหลดกลางทางคือ decode worker ของเราเอง (โหลดแบบ lazy ตอนใช้รูปแรก)
พร้อมกับ CSP `connect-src 'none'` ใน `public/_headers`

### 5. ℹ️ tolerance ที่ต่างกันตามเอนจิน
Firefox แสดงความต่าง 8–21 ระดับบนพิกเซลขอบมนไม่เกิน 0.006% ของภาพ
เพราะ tile cache composite partial alpha สองชั้น ขณะที่ export composite ชั้นเดียว
ยอมรับ โดยตั้ง tolerance เข้มที่สุดเท่าที่แต่ละเอนจินยอม (Chromium/WebKit ≤ 2 · Firefox ≤ 24)
**ฝั่งที่ถูกต้องคือไฟล์ที่ export** ผู้ใช้จึงได้ไฟล์ที่ดีเท่าหรือดีกว่าที่เห็น

## สิ่งที่ยังทำไม่ได้ และต้องพูดให้ชัด

1. **ยังไม่ได้ทดสอบด้วยมือบนเครื่องจริง** — สภาพแวดล้อมนี้เป็น headless Linux
   สามเรื่องที่ **ระบบอัตโนมัติแทนไม่ได้** และต้องทำก่อนปล่อยให้คนใช้:
   - คัดลอกแล้ววางจริงใน Slack / LINE / Jira / Gmail / Word
   - วางจาก **Windows Snipping Tool** และ **macOS Cmd+Shift+4** จริง
   - คัดลอกบน **Safari จริง** และ **Firefox จริง** (ADR-003 ยืนยันได้แค่ Chromium)
2. **Time-To-Copy ของมนุษย์ยังไม่ได้วัด** — วัดได้แค่ latency ที่แอปเพิ่มเข้าไป (69–210 ms)
   ตัวเลข "< 20 วินาที" ต้องจับเวลากับคนจริง 3 คนที่ไม่เคยเห็นแอป
3. **ไม่มีตัวบอกระดับซูม** — board ที่สูงมากถูกย่อลงให้พอดีจอ (เช่น 34%) แต่ผู้ใช้ไม่รู้
   นี่คือช่องว่าง UX ที่ชัดที่สุดของ Phase 1 → **งานอันดับแรกของ Phase 2**
4. ยังไม่มี: เลือก/ย้าย/ปรับขนาด, undo/redo, autosave, ครอบตัด, คำอธิบายภาพ (ตามแผน)

## ขั้นต่อไป — Phase 2

ตามลำดับความสำคัญที่ปรับจากสิ่งที่เห็นใน Phase 1:

1. **ซูมและ pan + ตัวบอกระดับซูม + ปุ่ม fit** — ช่องว่างที่ชัดที่สุดตอนนี้
2. เลือกวัตถุ / เลือกหลายวัตถุ / ย้าย / ปรับขนาด (พร้อม snapping)
3. ลากสลับลำดับในโหมด auto (เลข badge เรียงใหม่เอง)
4. ลบ / ทำซ้ำ / จัดลำดับชั้น
5. Undo / redo แบบ snapshot
6. Autosave ลง IndexedDB กันแท็บปิด
7. คีย์ลัดครบชุด

ก่อนเริ่ม Phase 2 **แนะนำให้ทดสอบด้วยมือตามข้อ 1 ข้างบนก่อน** เพราะถ้าการคัดลอกมีปัญหาบน
เบราว์เซอร์หรือแอปปลายทางจริง มันจะเปลี่ยนลำดับความสำคัญของงานทั้งหมด
